# Chat Session — Data Flow & Why We Store What We Store

This document explains the full data lifecycle of a chat session:
what the frontend sends, what the backend stores, what SSE does,
and why certain data must be persisted vs. what the backend always has.

## 1. The big picture

```
BROWSER (tab)                          BACKEND (Express)              DATABASE (MySQL)
─────────────────────────────────────────────────────────────────────────────────────
sessionStorage:                        req.cookies                    conversations table:
  session_id    ─── POST /api/chat ──► visitor_id      ──────────────► session_token
  utm_source          (body)           sessionToken    ──────────────► visitor_id
  utm_medium          body ──────────► utmSource       ──────────────► utm_source
  utm_campaign        body ──────────► message         ──────────────► utm_medium
  ...                                                                  utm_campaign
                                                                       ...
cookie:                                                               messages table:
  visitor_id ──── req.cookies ───────► visitor_id                     role, content, turn_index
                  (automatic)
```

The browser's `sessionStorage` is **per-tab and per-page-load** — it's wiped on
refresh. The backend's `conversations` table is the **persistent record** that
ties together all turns of a conversation, including the UTM context captured
at the very first message.

## 2. What the frontend sends on every message

Every `POST /api/chat` from the browser includes:

```typescript
// frontend/lib/chatbot/chatService.ts
{
  pageSlug:     'glp1-weight-loss-E',         // which page the chat is on
  sessionToken: '99bc1feb...',                // 64-char hex — from sessionStorage
  message:      'What is GLP-1?',             // the user's text

  // UTM params — read from sessionStorage (captured on landing)
  utmSource:     'google',
  utmMedium:     'cpc',
  utmCampaign:   'glp1-awareness',
  utmContent:    '',
  utmTerm:       'glp1 medication',
  utmCampaignId: '',

  // visitor_id is NOT sent in the body — backend reads it from the cookie directly
}
```

**Why send UTMs on every message?**
Only the first message creates the session — subsequent messages call
`getConversation(sessionToken)` which just looks up the existing row.
The UTMs in the body are only used on session creation (`createSession`).
Sending them every time is safe (they're ignored after the first turn) and
avoids a race condition where session creation could miss them.

## 3. What the backend always has — no need to store

These values are available on **every request** from the HTTP layer itself:

| Value | Where it comes from | Used for |
|---|---|---|
| `visitor_id` | `req.cookies.visitor_id` (cookie-parser middleware) | Identifying the returning user |
| `user-agent` | `req.headers['user-agent']` | UA parsing for device/browser/OS in analytics |
| `referer` | `req.headers['referer']` | `page_url` field in server-side analytics events |
| `ip` | `req.ip` (Express) | Anonymised IP in analytics |
| `pageSlug` | Request body | Which page the chat is on |
| `message` | Request body | The user's current message |

**These never need to be stored in the conversations table** — they arrive with
every request and the backend can always read them directly.

## 4. What the backend must store — and why

Some values are only available on the **first message** of a conversation.
Later turns don't re-send them (UTMs) or can't access them at event-emit time.

### `session_token` (primary key)
- **What:** 64-char hex generated by the frontend on page load (`sessionId.ts`)
- **Why stored:** links all turns of a conversation together. The backend uses it
  to look up existing conversation state (history, `ad_shown` flag, etc.)
- **What happens without it:** the backend would have no way to continue a
  conversation across multiple messages — every message would start fresh

### `visitor_id`
- **What:** UUID from the `visitor_id` cookie
- **Why stored:** server-side analytics events (`chat_turn`, `chat_session_started`)
  are emitted **after** the response is sent — the original `req.cookies` object
  is gone. Reading from the stored row guarantees the right visitor ID is attached
  to every server-side event, even on turn 5 of a conversation
- **What happens without it:** server-side `chat_turn` events would have an empty
  `user_visitor_id` — you couldn't join them with client-side events for the same user

### `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `utm_campaign_id`
- **What:** UTM params from the landing URL, captured in `sessionStorage` by
  `UrlParamCapture` and sent in the first chat request body
- **Why stored:** the backend fires `chat_turn` events mid-stream and post-stream.
  At that point there is no access to the browser's `sessionStorage`. Without the
  stored UTMs, you'd lose the campaign attribution on the most valuable events
  (the ones that tell you which campaign drove actual chat engagement)
- **What happens without it:** `chat_turn` events would have empty UTM fields —
  you couldn't answer "which Google campaign drove the most chat completions?"

### `ad_shown` (boolean flag)
- **What:** whether an ad card has already been sent in this conversation
- **Why stored:** the ad-selection CAS (compare-and-swap) uses this to guarantee
  **at most one ad card per conversation** across concurrent requests. It's an
  atomic UPDATE that flips `false → true` — only the winner delivers the card
- **What happens without it:** two simultaneous messages could both win the ad
  race and the user sees two ad cards

### `page_slug`
- **What:** which content page this conversation belongs to
- **Why stored:** needed to load the correct chatbot config (system prompt, model,
  metadata) on every turn — the frontend sends it in the body but storing it
  avoids relying on the client for correctness on subsequent turns

## 5. How SSE works and why we use it

### What is SSE?

Server-Sent Events (SSE) is a **one-way streaming protocol** over a normal HTTP
connection. The browser opens a connection and the server pushes data as it
becomes available — without the browser polling.

```
Browser                              Backend
  │                                     │
  │── POST /api/chat ──────────────────►│
  │                                     │  starts LLM stream
  │◄── HTTP 200 (text/event-stream) ────│
  │                                     │
  │◄── data: {"token":"GLP"} ───────────│  token arrives
  │◄── data: {"token":"-1"} ────────────│
  │◄── data: {"token":" works"} ────────│
  │◄── data: {"token":" by"} ───────────│
  │                    ...              │  (hundreds of tokens)
  │◄── data: {"adCard":{...}} ──────────│  ad card (if any) — after stream done
  │◄── data: [DONE] ────────────────────│  terminator
  │                                     │
  connection closes                     │
```

### Why not WebSockets?

| | SSE (what we use) | WebSockets |
|---|---|---|
| Direction | Server → client only | Bidirectional |
| Protocol | Plain HTTP | Upgraded TCP |
| Auto-reconnect | Built into browser | Must implement manually |
| Proxies/CDNs | Works out of the box | Often needs special config |
| Our need | Server streams tokens to browser | Not needed — browser only sends messages |

SSE is simpler and sufficient. The browser only ever sends one message per turn
(via POST body) — all the streaming goes server → client.

### What we stream

Three types of frames:

```
data: {"token":"GLP"}          ← one per LLM delta — browser appends to message
data: {"adCard":{...}}         ← at most once per conversation — browser renders AdCard
data: [DONE]                   ← signals stream end — browser stops the EventSource
```

### Why stream instead of wait for the full response?

Without streaming the user would see a blank chat bubble for 3-8 seconds, then
the full response appears at once. With SSE, tokens appear as the LLM generates
them — feels instant.

### How `[DONE]` is used

The frontend `useChatbot.ts` hook listens for `[DONE]` to:
1. Stop the typing indicator
2. Mark `isStreaming = false` on the message (which triggers full markdown parsing in `MessageContent`)
3. Allow the next message to be sent

Without `[DONE]`, the frontend would never know when the stream ended and would
keep the input disabled forever.

## 6. End-to-end walkthrough — first message

> User visits `weight.localhost:3000/glp1-weight-loss-E?utm_source=google`
> and types "What is GLP-1?"

```
1. PAGE LOAD
   UrlParamCapture.tsx runs:
     - getVisitorId()    → reads/creates UUID cookie "visitor_id"
     - initSessionId()   → generates 64-char hex, stores in sessionStorage "session_id"
     - captureUrlParams() → stores {utm_source: "google", ...} in sessionStorage

2. USER TYPES "What is GLP-1?" AND HITS SEND

3. FRONTEND builds POST body (chatService.ts):
   {
     pageSlug:    "glp1-weight-loss-E",
     sessionToken: "99bc1feb...",       ← from sessionStorage
     message:      "What is GLP-1?",
     utmSource:    "google",            ← from sessionStorage
     utmMedium:    "",
     ...
   }
   Cookie "visitor_id" = "d02898e2-..." is sent automatically by browser

4. BACKEND receives POST /api/chat:
   - Validates body with Zod
   - reads visitor_id from req.cookies.visitor_id = "d02898e2-..."
   - getConversation("99bc1feb...") → returns null (new session)
   - createSession("99bc1feb...", chatbotId, "glp1-weight-loss-E", {
       visitorId: "d02898e2-...",
       utmSource: "google",
       ...
     })  → inserts row into conversations table
   - trackEvent("chat_session_started", { sessionId: "99bc1feb...", ... })

5. BACKEND opens SSE stream:
   res.setHeader("Content-Type", "text/event-stream")
   → starts OpenRouter LLM call

6. TOKENS STREAM:
   data: {"token":"GLP"}
   data: {"token":"-1"}
   data: {"token":" works"}
   ...

7. STREAM COMPLETES:
   - saves assistant reply to messages table
   - trackEvent("chat_turn", { turn_type: "bot", response_time_ms: 3200, ... })
     ↑ reads visitor_id and utmSource from conversations row (not from req)
   - data: [DONE]

8. FRONTEND receives [DONE]:
   - marks message as complete
   - MessageContent re-renders with full markdown
   - ad_impression events fire (if rec-cards present)
```

## 7. End-to-end walkthrough — second message

> Same user, same tab. Types "How much does it cost?"

```
1. FRONTEND builds POST body:
   {
     sessionToken: "99bc1feb...",   ← SAME token — still in sessionStorage
     message:      "How much does it cost?",
     utmSource:    "google",        ← still in sessionStorage (tab not refreshed)
     ...
   }

2. BACKEND receives POST /api/chat:
   - getConversation("99bc1feb...") → returns existing row ✓
     (visitor_id = "d02898e2-...", utmSource = "google" — read from DB)
   - does NOT call createSession (session already exists)
   - loads message history from messages table (includes "What is GLP-1?" + reply)

3. BACKEND builds prompt:
   system_prompt + [prior messages] + "How much does it cost?"

4. SSE stream → tokens → [DONE]

5. trackEvent("chat_turn", {
     sessionId:    "99bc1feb...",
     userVisitorId: "d02898e2-...",  ← from conversations row, not cookie
     utmSource:    "google",         ← from conversations row, not sessionStorage
     turn_index:   2,
   })
```

**Key point:** on turn 2, the UTM and visitor_id come from the **conversations
row**, not from the live request. This is why they must be stored — if the user
had refreshed the tab between turn 1 and turn 2, `sessionStorage` would be wiped
and a new session would start. The DB record is the persistent truth.

## 8. Why analytics needs the conversations row

The analytics question: *"Which campaign drove the most engaged users?"*

To answer this you need to join:
- `chat_turn` events (server-side — no browser access)
- with their UTM attribution

```sql
-- Which UTM source drives the longest conversations?
SELECT
    utm_source,
    avg(JSONExtractInt(props, 'turn_index')) AS avg_turns,
    count()                                  AS total_bot_turns
FROM analytics.user_event_logs
WHERE event_name = 'chat_turn'
  AND JSONExtractString(props, 'turn_type') = 'bot'
  AND utm_source != ''
GROUP BY utm_source
ORDER BY avg_turns DESC;
```

This works because when `chat_turn` is emitted, `serverTrackContext` includes
`utmSource` read from the conversations row. Without storing UTMs in the
conversations table, this query would always return empty UTM fields for
server-side events.

## 9. What lives where — summary table

| Data | Lives in | Lifetime | Why there |
|---|---|---|---|
| `visitor_id` | Browser cookie | 2 years | Survives tab close, refresh — identifies returning users |
| `session_id` | `sessionStorage` | Per tab/page load | Scoped to one conversation |
| UTM params | `sessionStorage` | Per tab/page load | Captured from landing URL |
| `visitor_id` | `conversations` table | Forever | Server-side events need it after req ends |
| UTM params | `conversations` table | Forever | Server-side events need campaign attribution |
| `ad_shown` | `conversations` table | Per conversation | CAS lock — prevents duplicate ad cards |
| `session_token` | `conversations` table | Forever | Links all turns + joins ClickHouse ↔ MySQL |
| Message history | `messages` table | Forever | LLM context window for multi-turn chat |
| All analytics events | ClickHouse | 2 years (TTL) | Time-series analysis, funnels, CTR |

## 10. Data gaps — available on client but missing on server-side events

### Why the gap exists

The frontend sends everything in the POST body — `queryParams`, `referrer`, UTMs,
all of it. The backend **receives** all of it. The gap is not about what the
frontend sends — it's about **when server-side analytics events fire**.

```
Frontend sends POST /api/chat
       ↓
Backend receives request  ← req.body, req.cookies, req.headers — ALL available here
       ↓
createSession() — stores visitor_id + UTMs into DB   ← only these are saved
       ↓
LLM streams tokens...  (3–8 seconds pass)
       ↓
Stream completes → trackEvent("chat_turn") fires HERE
                                              ↑
                          req object is GONE at this point.
                          Only the conversations DB row is available.
```

The `req` object only lives for the duration of the HTTP handler. By the time
the LLM finishes streaming and `chat_turn` fires, `req.body` is out of scope —
only what was explicitly saved to the `conversations` row at the start remains.

**UTMs work because we stored them. `queryParams` and `referrer` don't work
because we chose not to store them.** The fix for any gap is always the same:
add the field to the `/api/chat` body schema, store it in `conversations` on
`createSession`, and include it in `serverTrackContext`.

---

Server-side events (`chat_session_started`, `chat_turn`, `ad_impression`) are
fired by the backend process. They have **no access to the browser** — no
`sessionStorage`, no `window`, no `document`. This creates gaps where rich
context the frontend has is simply absent from server-side events.

| Data | Available on client events? | Available on server-side events? | Why missing | How to fix if needed |
|---|---|---|---|---|
| `query_params` (full landing query string — `gclid`, `fbclid`, `utm_ad_id`, custom macros) | ✅ Yes — read from `sessionStorage` by `trackingClient` on every beacon | ❌ No — never sent to `/api/chat`, not stored in `conversations` | Frontend-only storage; backend has no way to read `sessionStorage` | Add `queryParams` to `/api/chat` body and store in `conversations` table, same as UTMs |
| `page_url` (exact URL at event time) | ✅ Yes — `window.location.href` at the moment the event fires | ⚠️ Partial — backend uses `req.headers['referer']` which is the URL the browser was on when it made the POST request. May differ if user navigated mid-stream | `window.location` only exists in the browser | Referer is good enough for most cases; for exact URL use client-side events |
| `referrer` (where user came from) | ✅ Yes — `document.referrer` | ❌ No — backend has no access to `document.referrer` | `document` is browser-only | Send `referrer` in the `/api/chat` body and store in `conversations` table |
| `device_type` / `browser` / `os` | ✅ Yes — parsed from `User-Agent` header server-side (same result) | ✅ Yes — same UA parsing | No gap — both paths parse the same header | N/A |
| `ad_title` on `ad_impression` (ads-table path) | ✅ Yes — `AdCard` fires client-side impression with `ad_title` | ⚠️ Partial — server fires `ad_impression` with `ad_title` from the ads row, but this fires before the AdCard reaches the browser | No gap in practice — server has the title from the DB | N/A |
| Scroll depth / time on page | ❌ Not tracked | ❌ Not tracked | Never implemented | Add client-side events with `IntersectionObserver` / `setTimeout` |
| Which specific `.rec-card` link was an impression (when same URL appears twice) | ✅ Yes — `impression_id` UUID added per link | ❌ N/A — server only knows a URL appeared in the reply text, not how many times it was rendered as a card | Server scans raw `fullText` string, not rendered DOM | Already handled client-side — server-side inline impression tracking was removed |

---

### The `query_params` gap in detail

This is the most impactful gap today. `query_params` contains the **full landing
query string** — including `gclid` (Google Click ID), `fbclid` (Facebook Click
ID), and any custom tracking macros. These are richer than just UTMs.

**What you can answer today:**
```sql
-- Which utm_source drove chat_turn events? ✅ (UTMs stored in conversations)
SELECT utm_source, count() FROM analytics.user_event_logs
WHERE event_name = 'chat_turn' GROUP BY utm_source;
```

**What you CANNOT answer today:**
```sql
-- Which specific Google ad (gclid) drove chat engagement? ❌
-- query_params is empty on chat_turn — it was never stored in conversations
SELECT JSONExtractString(query_params, 'gclid'), count()
FROM analytics.user_event_logs
WHERE event_name = 'chat_turn' GROUP BY 1;
-- → always empty
```

**To fix:** add `queryParams` to `chatRequestSchema` validation, pass it in
`chatService.ts` body, store it in `conversations` (new column or JSON blob),
and include it in `serverTrackContext`. Same pattern as UTM params.

---

### The `referrer` gap in detail

`referrer` on client-side events = `document.referrer` = the page the user was
on **before arriving at our site** (e.g. `https://google.com`).

`referrer` on server-side events = `req.headers['referer']` = the URL the
browser was on when it made the POST to `/api/chat` = **our own page URL**
(e.g. `http://weight.localhost:3000/glp1-weight-loss-E`).

These are completely different things. The true "where did this user come from"
referrer is only available client-side via `document.referrer`. If you need it
on `chat_turn`, it must be sent in the first `/api/chat` body and stored.

---

### Decision guide — when to fix a gap

Not every gap needs fixing. Ask:

1. **Do you need this field on server-side events specifically?**
   If the analysis can use client-side events instead (e.g. `page_view` already
   has `referrer`), don't add complexity to the chat pipeline.

2. **Is the field stable for the whole conversation?**
   UTMs are captured once on landing and don't change — worth storing.
   `page_url` changes if the user navigates — storing it once would be misleading.

3. **What's the query you actually want to run?**
   Write the ClickHouse query first. If it works with existing data, no fix needed.
